## Overarching mission and initial goals

The long-term work is not merely a collection of Web UI fixes. The agreed architecture is:

1. Incrementally extend and curate the shared OSDC semantic vocabulary in DotNetLibraries.
2. Bind each provider's actual fields to those meanings, including physical quantity, SI unit, coordinate/reference conventions, uncertainty semantics and contextual roles.
3. Keep the model, REST/OpenAPI, generated client, MCP contract, Web UI and documentation consistent.
4. Automatically manage an atomic capability for each enabled and available MCP tool from its complete discovered contract.
5. Automatically generate data-access capabilities over typed reachable outputs, including arrays, nested objects and semantically bound wrapper values.
6. Compose those generated layers with a relatively small set of generic semantic capabilities in DrillWeaver so planning, conditional decisions, recovery and replanning do not require a hand-authored workflow for every user question.

The curated catalogue owns shared meanings; providers own assertions that their fields express those meanings. Schema descriptions alone are insufficient. Capability generation must use input/output schemas, semantic extensions, effects/safety metadata and result envelopes, while preserving authorization and existing DrillWeaver executor protections.

The earlier handover contains the detailed governance and proposed runtime design. Its version numbers and inventory counts are historical; inspect current source and published packages before upgrades. Rig and SurveyInstrument were subsequently worked on in this conversation. Trajectory is the current provider under active development. Verify their present source rather than assuming every earlier change is deployed.

## Unresolved defect: Target TVD resets on blur/Tab

### User reproduction

The user runs the WebApp locally, opens the only Target Landing case, changes Target TVD from 1100 to 1500, and presses Tab. The field returns to 1100. A later attempt could briefly become worse, where typed digits were not displayed.

The same unit-input component works elsewhere in the application. The user correctly challenged the idea that the component itself is inherently broken.

### Current source shape

The editor currently uses the normal component shape, without `Immediate` and without an artificial component key:

```razor
<MudInputWithUnitAdornment QuantityLabel="Target TVD"
                           QuantityName="DepthDrilling"
                           DrillingSignalReference="DrillingSignalReferenceType.Depth"
                           SIValueNullable="@Plane.TVD"
                           SIValueNullableChanged="SetTargetTvd" />
```

and:

```csharp
private void SetTargetTvd(double? x)
{
    Plane.TVD = x;
    Plane.Z = x;
}
```

The generated WebPages DTO exposes TVD and Z independently, hence both are currently assigned explicitly. Source search found only the expected async case assignment in `TargetLandingEdit.OnInitializedAsync`; no second obvious TVD assignment was identified. `TargetLandingMain` polling updates its list and is cancelled when loading a selected case, but this still needs runtime verification.

### Failed or inconclusive attempts

- Adding `Immediate="true"` caused each keystroke to be parsed/formatted and made digit entry unusable. It was removed. Do not repeat this as the primary fix.
- Adding `@key="Plane"` did not solve the user's issue and was removed.
- An isolated Release WebApp on port 5091 did not reproduce the reset. Automated fill of `1500`, Tab, and a later parent rerender retained 1500. Manual digit entry in that isolated instance also committed successfully on leaving the field.
- Therefore the defect remains real in the user's actual local launch, but its trigger is absent from the isolated test. Do not claim it is fixed and do not reduce the investigation to “rebuild the WebApp”.
